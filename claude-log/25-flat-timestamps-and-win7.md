## 요청

> 이거 0으로 몇분 지속되는 데이터는 반영을 못하는 거 같아
> 그리고 win 7, win 10, win11 셋 모두에서 빌드하고 작동할 수 있게 해줘

## 답변

### 1. 먼저 확인한 것 — 0 자체는 문제가 없었습니다

"0 이 오래 이어지는 채널" 을 다섯 가지 모양으로 만들어 코어에 넣어 봤습니다.
열이 IO 인 배치 / 행이 IO 인 배치 / 처음부터 끝까지 0 인 채널 / 0 이 4500행 이어지는
채널 / 0 자리가 빈 칸인 경우. **전부 그대로 들어옵니다.** 표본이 하나도 빠지지
않고, 채널도 사라지지 않습니다. 회귀 시험으로 남겼습니다.

### 2. 진짜 원인은 **시간축**이었습니다 — 세 가지를 고쳤습니다

값이 아니라 **시각이 겹치면** 그 구간이 화면에서 사라집니다.

#### ① 같은 시각이 반복되면 한 점에 겹쳤습니다

실제 로그에서 흔한 두 가지 때문입니다.

- 시간 칸을 **값이 바뀔 때만** 적고 중간은 비워 두는 로그 (빈 칸은 직전 값으로
  채워지므로 결국 같은 시각이 됩니다)
- 기록 주기가 시간 표기의 해상도보다 빠른 경우 — **분 단위 표기에 초 단위 기록**

그러면 몇 분에 걸친 표본이 전부 같은 x 좌표에 놓입니다. 세로줄 하나로 뭉개져
**사실상 보이지 않습니다.** "0 으로 몇 분 지속되는 데이터가 반영이 안 된다" 가
이것이라고 봅니다.

**다음 서로 다른 시각까지의 사이를 고르게 나눠 펴도록** 고쳤습니다.

```
전:  10:00 10:00 10:00 10:00 10:00 10:01 …   ← 5개가 한 점에
후:  10:00 10:00.2 10:00.4 10:00.6 10:00.8 10:01 …
```

순서는 그대로이고, **서로 다른 시각으로 적힌 표본의 자리는 건드리지 않습니다.**
몇 개를 폈는지 상태 표시줄에 알려 줍니다.

#### ② 시각이 전부 같으면 아무것도 안 그려졌습니다

"값이 증가하지 않으면 샘플 번호로 물러선다" 는 규칙이 **줄어들 때만** 걸리고
**평평할 때**는 걸리지 않았습니다. 그래서 시간이 전부 같으면 가로 폭이 0 이 되어
화면에 아무것도 남지 않았습니다. 이제 샘플 번호로 물러섭니다.

#### ③ 시간 열에 빈 칸이 있으면 시간축으로 못 알아봤습니다

시간축 후보를 셀 때 **빈 칸에서 구간을 끊고 있었습니다.** 시간 칸을 값이 바뀔 때만
적는 로그에서는 진짜 시간 열이 길이 1짜리 후보로 전락하고, 값이 계속 증가하는
데이터 열(누적 카운터 등)이 대신 시간축으로 뽑혔습니다. 빈 칸은 이제 구간을 끊지
않습니다 (길이에는 더하지 않으므로, 거의 비어 있는 줄이 이기지도 않습니다).

### 3. Windows 7 · 8 · 8.1 · 10 · 11 — 실행 파일 하나로

| 한 일 | 왜 |
|---|---|
| API 수준을 **Windows 7 로 고정** (`_WIN32_WINNT=0x0601`) | 7 에 없는 함수를 실수로 부르면 **컴파일 단계에서** 걸립니다 |
| MSVC 에서 **CRT 를 정적으로** 링크 | 기본값은 `ucrtbase.dll`·`vcruntime140.dll` 을 요구하는데 갓 설치한 7 에는 없습니다. **이것이 7 에서 안 돌던 가장 큰 이유입니다** |
| 서브시스템 판 **6.01** | 6.02 로 박히면 7 이 "올바른 Win32 응용 프로그램이 아닙니다" 로 거절합니다 |
| 매니페스트에 **7 / 8 / 8.1 / 10·11** 모두 선언 | 빠진 판에서는 호환 shim 이 걸립니다 |
| `WM_DPICHANGED` 를 직접 정의 | 8.1 부터 선언되는 값이라 헤더가 감춥니다 |
| `.xlsx` 를 못 여는 구성이면 "지원하지 않는 형식" 으로 | CSV 로 저장하면 된다는 뜻이 전해집니다 |

7 이후에 생긴 기능은 **전부 `GetProcAddress`** 로 씁니다 —
`SetDefaultDllDirectories`(7 은 KB2533623 필요), `SetProcessDpiAwarenessContext`,
`GetDpiForWindow`, `DwmSetWindowAttribute`.

**빌드한 결과를 직접 확인했습니다** (mingw 크로스 빌드 산출물):

```
MajorSubsystemVersion 6 / MinorSubsystemVersion 1        ← Windows 7 로드 가능
정적 임포트에 7 이후 함수: 없음                            ← 전부 GetProcAddress
logscope.exe → d2d1 · DWrite · ole32 · shell32 · user32 · imm32 · advapi32
logcore.dll  → XmlLite · shlwapi · ole32
```

전부 Windows 7 에 기본으로 들어 있는 것들입니다 (OPC Packaging API 도 7 부터).

정적 CRT 의 대가는 exe 와 dll 이 **각자 자기 힙**을 갖는다는 점입니다. 한쪽에서
잡은 메모리를 다른 쪽에서 놓으면 안 되는데, 이 프로젝트의 경계는 처음부터 그렇게
되어 있습니다 (`logcore.h` — 넘기는 것은 전부 DLL 이 소유하고 `lc_close` 가 놓습니다).

### 검증

mingw 크로스 빌드 Debug/Release **경고 0**, 코어 테스트 **450개 통과** (388 → 450).
서브시스템 판과 임포트 목록을 실제 산출물에서 확인했습니다.

**MSVC 로는 빌드해 보지 못했고, 어느 Windows 에서도 실행해 보지 못했습니다**
(여기에 Windows 가 없습니다). 특히 확인 부탁드릴 것:

- **Windows 7 에서 실제로 실행되는지** — 이번 변경의 핵심입니다
- 정적 CRT 로 바꿨으니 Visual Studio 2017 빌드가 그대로 통과하는지
- 문제의 그 로그를 열었을 때 0 구간이 이제 보이는지, 상태 표시줄에 "같은 시각이
  적힌 표본 n개를 폈습니다" 가 뜨는지 (뜬다면 원인이 맞았다는 뜻입니다)
- 뜨지 않는데도 여전히 안 보인다면, 그 파일의 시간 열이 어떻게 생겼는지 알려
  주세요 — 다른 원인입니다
