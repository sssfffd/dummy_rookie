# 26 · 로그 여는 시간 — 표를 옮겨 담지 않게

- **판** 0.03
- **날짜** 2026-09-09
- **커밋** 이 커밋
- **바뀐 파일** `src/core/dataset.cpp`, `CMakeLists.txt`, `README.md`

## 요청

> 근데 로그 여는데 시간 오래걸리는 건 어쩔 수 없나?

## 답변

어쩔 수 없지 않습니다. 재 보니 **한 단계가 통째로 낭비**였습니다.

### 무엇이 낭비였나

로그를 열면 이렇게 흘렀습니다.

```
파일 → (XML/CSV 해석) → 격자 Grid → [머리말 잘라내기] → [뒤집기] → 채널
                                      ↑ 격자를 옮겨 담음   ↑ 격자를 한 벌 더 만듦
```

**열이 IO 인 배치**(우리 로그가 그렇습니다)에서는 격자를 통째로 뒤집었습니다.
1000만 칸짜리 로그면 그것만으로 **같은 크기의 격자가 하나 더** 생깁니다. 메모리가
두 배가 되고, 칸 하나하나를 옮기는 시간도 그대로 듭니다.

### 무엇을 했나

**옮기지 않고 첨자를 바꿔 읽습니다.** 머리말 건너뛰기도, 뒤집기도 읽는 자리에서
계산합니다 (`View`). 빈 줄을 지우던 것도 "쓸 줄 번호만 모아 두기" 로 바꿨습니다.

같은 입력(채널 200개 × 표본 5만개 = 1000만 칸)으로 세 번씩 재 본 결과입니다.

| | 전 | 후 |
|---|---|---|
| 표 → 채널로 만들기 | 1.3 ~ 2.4 초 | **0.5 ~ 0.8 초** |
| 최대 메모리 | 926 MB | **543 MB** |
| 칸당 메모리 | 97 바이트 | 57 바이트 |

대략 **2.5~3배** 빠르고 메모리는 **41% 적습니다.** 큰 파일에서 `LC_ERR_MEMORY` 로
못 열던 것도 그만큼 여유가 생깁니다.

동작은 하나도 바뀌지 않아야 하는 변경이라, 코어 테스트 450개(두 배치 모두 다룹니다)로
확인했습니다.

### 아직 남은 것 — 정직하게

이번에 고친 것은 **"격자 → 채널"** 단계입니다. `.xlsx` 를 열 때는 그 앞의
**XML 해석**이 더 오래 걸립니다 (zip 을 풀고 sheet.xml 을 칸마다 훑는 일).
그 부분은 Windows 전용(XmlLite)이라 여기서는 재 볼 수가 없어, 얼마나 차지하는지
말씀드릴 수 없습니다.

더 줄일 수 있는 방법 두 가지가 남아 있습니다. 원하시면 하겠습니다.

1. **칸 하나를 57 → 24 바이트로.** 지금은 칸마다 문자열 자리를 통째로 들고 있는데,
   숫자 로그에서는 대부분 비어 있습니다. 문자열을 따로 모아 두고 번호만 들면
   메모리가 절반 아래로 떨어지고, 그만큼 읽는 속도도 붙습니다.
   대신 두 리더(xlsx/csv)를 함께 고쳐야 하는데 **그쪽은 Windows 전용이라 제가
   시험해 볼 수가 없습니다.**
2. **한 번 읽은 파일을 저장해 두기.** 두 번째부터는 XML 해석을 통째로 건너뛰어
   거의 즉시 열립니다. 세트를 오갈 때마다 다시 읽는 지금 구조에서는 이게 체감이
   가장 클 수 있습니다. 대신 캐시 파일이 생기고, 원본이 바뀌었는지 확인하는 규칙이
   하나 늘어납니다.

**Windows 에서 실제 로그로 재 보지는 못했습니다.** 얼마나 빨라졌는지 알려 주시면
다음 손볼 곳을 정하는 데 도움이 됩니다.
